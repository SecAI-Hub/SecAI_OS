# Audit verifier enrollment and recovery

The periodic verifier requires an explicitly initialized, private enrollment ledger. Installing the updated files does **not** initialize it. Before initialization, the verifier fails closed and the UI reports unknown or degraded audit evidence. The installer and full native Fedora service lifecycle have not yet been qualified for this ceremony.

The root-owned format manifest is version 2. Every entry declares its associated systemd services, or an empty list for event-only logs. Version 1 manifests remain readable during an explicit upgrade; their absent service lists mean that service activity is not assessed for those entries. `required:false` permits an absent log only before any requirement or evidence has been observed. It never exempts an enrolled log.

## What the verifier establishes

- Observing a log, a Python archive/checkpoint, a configured requirement, or an active/starting/reloading/stopping/failed associated service permanently requires that log. An inactive service with no observed evidence is `not_applicable`; this is not proof that it never ran before enrollment or between verification polls. A failed service or unavailable systemd query cannot be called inactive. Offline mode does not clear requirements. Deactivating a service does not retire its evidence.
- Verified log identity, length and prefix digest are recorded independently under `/var/lib/secure-ai/audit-verifier/enrollment.json`. Deletion, inode replacement, truncation, changed prefixes and disappeared archives fail verification across process restarts. Existing Python checkpoints are verified with their key and full chain; even an unverified leftover checkpoint conservatively prevents missing-log exemption. Checkpoints are not external rollback anchors.
- Files are opened without following symlinks and must be single-link regular files. The verifier copies bounded snapshots, checks file identity and stability, and verifies only those snapshots. Keys must be owner-controlled, single-link regular files with mode 0400 or 0600. A concurrent append makes the check `unavailable` with `retryable:true`; it does not assert corruption or advance that log's verified prefix. Verification performs one bounded attempt, so a continuously busy writer can remain unavailable until a stable snapshot is obtainable.
- Python keyed chains must contain authenticated records; a legacy unkeyed chain is not accepted as keyed. MCP linkage remains classified as unkeyed. Structured JSONL remains **syntax-only**. The private prefix ledger detects later changes relative to a verified observation, but does not authenticate what a writer originally recorded.
- A missing, corrupted or unsafe private ledger is never recreated by normal verification. Missing or changed previous public report bytes latch `evidence_lost` in the private ledger. Later reports remain degraded until a reviewed offline reconciliation. A crash between the durable ledger and report writes is deliberately detectable on restart, even when caused by an ordinary interrupted write.

The public report keeps the existing `/var/lib/secure-ai/logs/audit-verify-last.json` path. It is root-owned, mode 0640, in the log directory's group (`secure-ai-logs` in the appliance). The verifier writes `checking` before processing logs, then fsyncs the final report. The file is updated in place so the recurring unit needs write access only to that inode, not the log directory. Partial reports cannot establish readiness. The UI expires successful reports after 35 minutes and describes the mixed assurance classes. A historical report is a point-in-time observation, not an egress authorization or continuous health guarantee. If a status file is unwritable, publication can fail; the unit exits unsuccessfully and any old UI report expires, rather than proving current verification.

## Deliberate installation or upgrade

Do this only as a reviewed local-administrator maintenance operation on the target appliance; these instructions are not an authorization to change live credentials or audit history.

1. Preserve the existing logs, archives, checkpoints, previous report, manifest and verifier version together in an administrator-controlled backup. Preserve ownership and modes, and record hashes. Do not delete the old evidence to make initialization pass.
2. Stop the audit timer and any concurrent verifier, and quiesce the affected writers while adopting their evidence. Review which services and event-only logs should already exist. An old installation with neither log nor checkpoint has no trustworthy historical enrollment signal; review that absence explicitly. This implementation does not reconstruct service history.
3. Install the verifier, manifest and both units. Provision the existing five audit credentials through the established credential mechanism; this upgrade does not change keys. `secure-ai-audit-enroll.service` and the recurring verifier use identical `LoadCredential` mappings. Confirm the log directory remains root-owned, group `secure-ai-logs`, mode 3770. If a historical report has a different owner, unsafe mode, or incorrect group, preserve it and make a separately reviewed ownership/mode correction; the enrollment command refuses to silently take over another owner's file.
4. With no existing enrollment ledger, run `sudo systemctl start secure-ai-audit-enroll.service`. This explicitly adopts existing valid evidence and creates the private mode-0700 state directory, mode-0600 ledger and mode-0640 public report. A safe existing public report is retained privately as `pre-enrollment-result.json`. An unsuccessful initial verification can still persist observed requirements; inspect the failed report instead of trying to reinitialize it. The enrollment unit has no installation target or timer and is absent from profile and UI activation paths.
5. Inspect the complete report and private ledger. Resume the intended writers, run `sudo systemctl start secure-ai-audit-verify.service`, and require the expected coverage. Only then resume the existing audit timer. Service-state lookup through local systemd must work from the installed sandbox. A service that becomes active without a log will make verification fail even if it was inactive during initialization.

Do not invoke the script with a generic source credentials directory and assume its filenames match: the shipped manifest names correspond to the systemd credential copies. The standalone CLI supports `AUDIT_HMAC_KEY_DIR`, `AUDIT_LOGS_DIR`, `AUDIT_FORMAT_MANIFEST`, and `AUDIT_VERIFIER_STATE_DIR` for controlled fixtures or reviewed offline operation. Neither unit performs implicit enrollment, credential migration, or retirement of previous requirements.

## Recovery, rotation and rollback limits

Normal verification never resets `required`, discards verified prefixes, adopts a replacement inode, or clears `evidence_lost`. Re-running `--initialize` against an existing ledger is rejected without overwriting its report. Manifest semantic changes also fail until a reviewed offline reconciliation preserves the accumulated obligations.

There is currently **no automatic reconciliation, retirement, rotation migration, or rollback command**. Preserve damaged and previous state, stop affected writers and the verifier, compare against separately retained evidence, and design/review the required transition before altering enrollment. A restored file commonly has a different inode and needs such a transition even if its bytes match. Ordinary logrotate and Python archive rotation can therefore intentionally degrade this verifier; a coordinated retention protocol remains required. Do not work around that failure by deleting the ledger. Logs are bounded to 128 MiB each, 128 evidence files, and 512 MiB per snapshot; reaching a bound fails closed and requires a reviewed retention decision.

The upgrade leaves writer log formats, keys and history bytes unchanged. Preserving the prior binaries, manifest and full state makes the source/configuration change reviewable and reversible, but reverting to the old verifier would remove disappearance enforcement. Such a downgrade must be treated as unverified audit coverage, not a supported security-preserving rollback. A validated state migration and integrated first-boot/upgrade workflow are still required.

The private ledger separates verifier evidence from compromised writer accounts; it does not resist a privileged attacker who can replace the whole private ledger and its corresponding history, nor prove integrity before initial enrollment. TPM-backed or independently stored checkpoints, external rollback anchors, tested retention, and writer-side durable acceptance before security-sensitive actions remain separate requirements. Periodic verification cannot detect an otherwise invisible closed writer descriptor until evidence or service readiness changes, and cannot itself deny a new external action. This change is not a production-readiness claim.
